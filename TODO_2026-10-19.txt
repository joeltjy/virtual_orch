0. sustain pedal clears the playback queue
=====================================================================
--- Description (from you) ---
  If the pedal is pressed down at time t, clear all the notes in the playback queue.
  FINAL RULE (from you, replacing "past t + 1 s", then "past t + 0.3 s"):
    - a note that has NOT started sounding yet does not sound (it is removed from the queue);
    - a note that IS sounding ends by t + 0.3 s (its note-off is moved up to at most t + 0.3 s;
      a note that would end earlier anyway is left alone).
  So t + 0.3 s (30 cs) is now only the latest end time of notes already sounding; the cut-off
  for queued notes is t itself.

--- What exists today (read from the code, not run) ---
  1. MidiInputProcess::handleSustainPedal (MidiInputProcess.cpp ~line 357): CC64 with value
     >= 64 is "pedal down" and calls activeReduction().setGenerationPause(true); value < 64
     resumes. It does not clear anything itself. (The pedal can come from the play keyboard
     or from a separate pedal keyboard.)
  2. The reduction thread's run loop calls ReductionTransformer::
     maybeEmitGenerationPauseSoftStopClear() when generation is stopped. ONLY on the
     transition not-paused -> paused it pushes a ClearQueue token with time = clock now +
     100 cs (now + 1 s) through pushOutputToken.
  3. That token goes (a) to outputTokenQueue, which OutputPlayback drains for the reduction
     monitor, and (b) to the orchestration transformer, which pulls it out of the reduction
     stream (extractClearQueueTokens), bypasses the orchestration model and pushes it to
     OutputPlayback in front of nothing else (OrchestrationTransformer.cpp ~line 516).
  4. OutputPlayback::applyClearQueue erases every NOT-YET-PLAYED note in its queue
     (nextTokens) whose onset is >= the clear time. Notes that start before t + 1 s still
     play, and notes already sounding are not cut.
  So the behaviour you describe exists in outline: pedal down -> pause -> notes starting
  after about now + 1 s are removed from the playback queue.

--- Where the +1 s lives today (what the change to 0.3 s would touch) ---
  The offset is Config::TimeResolution (100 cs) added to the clock in five places:
    - ReductionTransformer::maybeEmitGenerationPauseSoftStopClear   (the pedal / pause clear)
        app/source/reduction/ReductionTransformer.cpp:122
    - the same "clock now + 1 s" ClearQueue sent when input arrives while generation is
      stopped (overflow pause), in each transformer's run loop:
        ReductionTransformerV1.cpp:123, ReductionTransformerV2.cpp:229,
        ReductionTransformerPianoReduction.cpp:231, MusicTransformer.cpp:120
  Open point (0.6): the pedal clear and the overflow-pause clear share this one value in
  the code. Should only the PEDAL clear use 0.3 s and the other clears keep 1 s, or all of
  them move to 0.3 s?

--- Gaps I can see in the current code (my reading, not tested) ---
  a. The clear time is taken on the REDUCTION THREAD when it next loops, not at the moment
     the pedal arrives, so t is late by up to one loop iteration (a model call can take
     tens to hundreds of ms), and the clear is not sent at all if that thread is not
     running or is stuck.
  b. It is edge-triggered on the pause flag: if generation is already paused (the Launchpad
     pause pad, overflow pause, or a previous pedal press without release), pressing the
     pedal again sends no clear.
  c. In the soft stop of the overflow pause the code uses the same mechanism, so a pedal
     press that happens while an overflow pause is active is not distinguished.
  d. Only notes already in OutputPlayback's queue are cleared. Notes the orchestration
     transformer has not yet produced from reduction tokens already queued are still
     produced after the clear.

--- Answers (from you) ---
  0.1 The clear takes too long.
  0.2 Yes: clear on every pedal-down press, stamped with the pedal message's arrival time.
  0.3 Notes already sounding are CUT.
  0.4 Yes, the pedal still pauses generation; the problem is that the transition takes too long.
  0.5 Yes: clear both playback sources and drop the reduction tokens not yet processed (with
      the final rule: the ones with onset after t).
  0.6 The 0.3 s applies only to the pedal clear (the overflow-pause and other soft-stop clears
      keep 1 s).

--- Why it is slow today (my reading of the code) ---
  The pedal only sets generationPause. The ClearQueue token is created later, on the reduction
  thread, the next time its loop runs and notices the pause (the loop is busy for a whole model
  call). It then travels through the orchestration transformer, whose loop pulls it out only
  after its own iteration, and finally reaches OutputPlayback, which applies it. So the delay is
  up to one reduction-loop iteration plus one orchestration-loop iteration, and the clear time
  is stamped late as well.

--- Plan (small steps) ---
  1. FAST PATH: when the pedal goes down (MidiInputProcess::handleSustainPedal, on the MIDI
     thread) read the app clock at that instant, t, and hand a clear request {t + 30 cs} straight
     to OutputPlayback through a new small queue/atomic that its loop checks at the top of every
     iteration. It does not wait for either transformer thread. Generation is paused at the same
     moment as today.
  2. OutputPlayback applies the request (final rule): erase EVERY not-yet-sounded note from its
     queue (nextTokens), whatever its onset, and for notes already sounding (currentlyPlaying)
     move the note-off up to min(natural end, t + 30 cs) using the existing note-off path (the
     one flushModelSchedule uses); if t + 30 cs has already passed, send the note-off at once.
     Both playback sources are handled (the orchestration queue and the reduction monitor
     queue; they share nextTokens).
  3. SLOW PATH, kept for what is still upstream: also send the existing ClearQueue token, but
     stamped with t (the pedal time, not the reduction thread's clock) and applied as "drop every
     note with onset after t", so notes the reduction thread and the orchestration transformer
     have queued or are about to produce are dropped too (your 0.5, gap d; with the final rule
     the cut-off for notes that have not started is t, not t + 0.3 s). It must not be emitted only on
     the not-paused -> paused edge (your 0.2).
  4. Other soft-stop clears (overflow pause in V1, V2, PianoReduction, MusicTransformer) are
     NOT changed: they keep 1 s (your 0.6). Only the pedal path uses 0.3 s.
  5. Check: log the time from the pedal message to the first note-off / queue clear to see
     the latency drop.

--- Questions ---
  0.7 (answered, your rule: "if a note hasn't sounded it shouldn't sound; else if it's sounding,
      end by t + 0.3". In the example (press at 10.0 s): A (sounding, would last to 12.0 s) is
      cut to end at 10.3 s; B (queued to start at 10.2 s) and C (queued for 10.5 s) never
      sound.)
  0.8 (answered: yes. The fast path clears the playback queue at once, and the stamped ClearQueue
      token follows later for the upstream leftovers.)

1. vocsep modularity
=====================================================================
Target: the orchestration transformer.
Goal: the vocsep ensembling step should be easy to turn on/off and apply to ANY
orchestration transformer, not just one.

--- What is done today (read from the code, not run) ---

How voice ids get to the orchestration side:
  - VoiceSeparation (app/include/VirtualOrch/vocsep/VoiceSeparation.h) is an ONNX
    model (vocsep_reduction_best -> vocsep.onnx), loaded once in AppSession.
  - ReductionTransformer::pushOutputToken (app/source/reduction/ReductionTransformer.cpp)
    calls voiceSeparation->stampVoiceId(token, outputHistory) on every generated
    note, writing Token::voiceId (-1 = unset). Only done if vocsep is loaded
    (AppSession::bindActiveMusicBackend sets reduction.voiceSeparation).
  - The stamped token is then pushed to orchestrationReductionIncoming, so the
    orchestration model receives notes that already carry voiceId.
  - Vocsep can RE-stamp earlier notes. Those re-stamps only update the reduction's
    own outputHistory; I found no code forwarding them to the OT (see risk below).

The ensemble itself (IodPretrained only):
  - Lives inside IodPretrained::ensembleComboB
    (app/source/orchestration-models/IodPretrained.cpp ~line 384), called from
    IodPretrained::getOutput (~line 579) when ensembleEnabled is true.
  - Per note, the model samples a raw combo "A". With ensembling on, A is turned
    into an effective combo "B":
      1. B0 = the previous same-voice note's B (or A if first in its voice, or if
         voiceId < 0).
      2. Look at the last <=10 same-voice notes' raw A combos. For every
         (instrument x octave-delta) pair, compute the proportion of those notes
         whose A contains it.
      3. Add the pair to B if proportion > addP (default 0.67); remove it if
         proportion < removeP (default 0.3).
      4. Apply IOD-specific filters: outer-voice delta rules (+1/-1 octave vs
         temporally overlapping notes) and unique-octave filter.
  - B (not A) is what gets written back into combo_in for later notes (teacher
    forcing) and what gets decoded to output notes.
  - With ensembling off, B = A. If vocsep is not loaded (voiceId = -1 on every
    note) the "same voice" set is just the note itself, so it effectively does
    nothing.
  - Constants: ensembleHistoryNotes = 10, ensembleAddPDefault = 0.67,
    ensembleRemovePDefault = 0.3 (IodPretrainedTypes.h).

Switch / plumbing (all IOD-specific right now):
  - State: ensembleEnabled (default false), ensembleAddP, ensembleRemoveP are
    atomics ON IodPretrained, with setters/getters (IodPretrained.h).
  - UI: the "IOD Voice Ensemble" toggle + Add P / Remove P sliders in
    ReductionTemperatureWidget. Its tooltip says it needs vocsep loaded and does
    not enable voice separation itself.
  - Persistence: presetStore.settings -> "orchestration" child, keys
    vocsepEnsemble, vocsepEnsembleAddP, vocsepEnsembleRemoveP.
  - Wiring: dynamic_cast<IodPretrained*>(orchestrationModel) in THREE places:
    AppSession constructor (~line 188), AppSession::setOrchestrationModel
    (~line 337), and ReductionTemperatureWidget. If the active model is not
    IodPretrained the toggle does nothing.

Other orchestration models (OrchestrationModels.cpp factory: TestModel,
InstrumentCombinations, IodPretrained):
  - InstrumentCombinations and TestModel have no ensembling and never read
    Token::voiceId.
  - OrchestrationModel (base class) has no notion of vocsep or ensembling.

--- Why it is not modular today ---
  a. The algorithm (steps 1-3 above) is mixed with IOD-specific data types
     (pairsFromCombo / comboFromPairs, outer-voice delta filters) in one method.
  b. The enable flag and add/remove parameters live on the subclass, so every
     caller needs a dynamic_cast.
  c. The UI toggle is labelled and wired for IOD only.

--- Decisions from you ---
  - The on/off switch is GLOBAL, placed next to the orchestration model dropdown
    (not per model).
  - Any orchestration model that keeps a list of note quads (onset, dur, pitch, vel)
    as history should be compatible.
  - The same Add P / Remove P apply to every model.

--- Do the models keep such a list? (checked in the code) ---
Short answer: all three keep a note list, but only IodPretrained keeps the
per-INPUT-note record that ensembling needs.
  - All three (IodPretrained, InstrumentCombinations, TestModel) keep
    `history`: vector<OrchestrationNote> = the OUTPUT notes (Token with onset, dur,
    note, velocity, plus localInstrumentId), one entry per instrument per input note.
    The base class also keeps `tokenHistorySequence` (flat ints, used as model
    context).
  - IodPretrained additionally keeps `noteStream`: one StreamNote per INPUT note =
    the input Token (including voiceId) + raw combo A + effective combo B. This is
    what ensembleComboB reads.
  - InstrumentCombinations: the per-input-note combo is only in tokenHistorySequence
    as 9 ints per note (quad + GROUPS + 4 family slots). voiceId is NOT kept: its
    input tokens are flattened to ints (time/dur/pitch/vel only), and its output
    notes are rebuilt without copying voiceId.
  - TestModel: history copies the incoming Token (so voiceId survives), but each
    note gets exactly one instrument, and tokenHistorySequence is just the 4-int quad.
So today only IodPretrained has everything ensembling needs. To make "any model
with a note list" work, the ensemble needs, per input note: voiceId + the set of
"keys" the model chose for that note (A) + the effective set (B).
  - IOD key = (instrument x octave-delta) pair (existing pairsFromCombo).
  - InstrumentCombinations key = local instrument id (0-19). GROUPS and family
    tokens are bitmasks over instruments, so key set <-> tokens converts both ways.
  - TestModel key = its single instrument id.

2. mb + double anticipation  ->  new MelodyFirstReductionTransformer
=====================================================================
Goal: a new reduction transformer called MelodyFirstReductionTransformer, placed
with the other reduction transformers (app/include/VirtualOrch/reduction/ and
app/source/reduction/). Like the others it has a run() loop. The description is
being given step by step; only step 1 is described so far.

--- Step 1 (from you): keep a running melody+bass list R for instrument 0 ---
In each loop iteration:
  - Incoming MIDI is put on instrument 0. Keep the FULL list of all incoming
    MIDI notes, L.
  - Make sure notes are q5v8 first.
  - Keep a running list R of instrument-0 melody + bass. Every time a note is added
    to L, also add it to R, then run algorithm A (the same logic used to
    preprocess melody+bass for instrument 0 in training) on the LAST 2 SECONDS of R
    to get the true melody and bass.

--- What I found for algorithm A (read from ~/orchestration, read-only) ---
Main file: src/orchestration/preprocessing/melody_bass.py, function
skyline_and_bass(notes) -> (melody segments, bass segments, skyline_ticks).
It is purely rule-based (no model) in "version 1". Per note of duration D, with
T = min(33% of D, 100 ms):
  1. Melody cover test: drop a note if a strictly HIGHER pitch overlaps
     [onset+T, offset-T], or a higher pitch starts within 30 ms of its onset.
  2. Bass cover test: same, but for a strictly LOWER pitch.
     Any note kept as melody by the cover test is blocked from bass
     (unless it is later removed as a trough).
  3. Repeated-note chains: a chain of >=4 notes on one pitch whose gaps to the next
     same-pitch note all lie within 40 ms of each other is removed from the
     melody (including the note the chain lands on).
  4. Troughs: a melody run under 1 s whose neighbours on both sides are >=13
     semitones above it is removed (and may become bass). A single melody note
     under 0.5 s with both neighbours >10 semitones above is also removed.
  5. An earlier note that overlaps a later onset is cut off at that onset.
  6. Then keep only the tick-wise top line (melody) / bottom line (bass). A note
     keeps only the ticks it wins; if less than half remains, it is dropped.
     NOTE (corrected after your remark): only this last, monophonic stage shortens
     notes (steps 5 and 6: cut at the next onset, then keep the top/bottom line).
     The earlier stages (cover test, chains, troughs) keep or drop a note WHOLE.
"Version 2" (vocsep): keeps WHOLE melody notes from vocsep voices that the skyline
votes for (vocsep_melody_indices); bass is unchanged from version 1.
Which version produced the instrument-0 data for T8? I believe version 1
(maestro_melody_bass_plain_amt.py reads the "skyline/" directory built by
scripts/build_melody_and_bass.py, and melody_bass_intervals.py calls
skyline_and_bass directly). I did not confirm this against the phase-2 build.
Input to A offline: all notes of a piece, with start/end in ticks AND seconds,
sorted by (onset, pitch, offset), i.e. note durations are fully known.

--- Answers from you ---
  1. Algorithm A = version 1 (rule-based skyline_and_bass).
  2. Window = the 2 seconds before the onset (of the newest note). CHANGED later: now
     t - 2 s to the current time t, notes truncated to t (see the CHANGE section).
  3. A's result REPLACES the notes in that window of R.
  4. When a note-off arrives, update L and R.
  5. q5v8 floor is 5 cs. R and A only see snapped notes.
  6. Everything stays on instrument 0.
  7. Inherit from ReductionTransformer.
  Change requested: "run the 2 s check on R only ONCE per mass pull" (not once per
  note). So: drain everything the queue holds, add all of it to L and R, then run A

--- Do short bursts arrive together, and does run() pull them together? ---
(Checked by reading the code. I did not run the app with live MIDI.)

Consumer side (reduction run loop): YES, it pulls everything.
  - V1/V2/PianoReduction call applyQueuedInputToInputData() once per loop iteration,
    which is `while (inputTokenQueue.pull(inputToken))`: it drains every token that
    is in the queue at that moment. Then applyUpdatesFromFilter() drains all pending
    note-off updates the same way. So "one mass pull per iteration" is already how
    the existing loop works, and the new class can run A once right after the drain.
  - While the loop is busy generating (an ONNX call takes a while), more notes pile
    up and are drained together on the next iteration.

Producer side (MidiInputProcess, Direct input mode): bursts ARE grouped, but not
guaranteed to arrive as one pull:
  a. Grouping works like this. Each note-on is stored with its real onset, and a
     10 ms timer is started. The timer does nothing until there has been a quiet
     gap longer than directInputWindowLength (default 10 = 0.1 s) since the LAST
     note-on. Then it flushes ALL unflushed notes in one timer callback, each
     keeping its own real onset. So a burst whose gaps are all <= 0.1 s is flushed
     together.
  b. NOT atomic. The flush pushes tokens one at a time into inputTokenQueue
     (sendTokensToMusicTransformer -> inputFilter->filter -> push), with std::cout
     prints between pushes. The reduction thread can drain in the middle, so one
     burst can be split across two loop iterations (first part, then the rest). A
     two-pull burst would run A twice.
  c. (CORRECTED) Fast playing does NOT wait for a pause when note-offs are sent
     (directInputSendNoteOffs is true by default and in the version0.1/0.2 presets).
     A note whose key is released before the quiet-gap flush is sent at its
     note-off, with its real onset and its final duration (see the 5 s passage
     section below). Only notes still HELD wait for the flush.
  d. Note-offs take a different path. For a note that is already flushed, the
     note-off becomes a TokenUpdate (old duration -> held duration) via
     updatesFromFilter, drained after the input drain. For a note not yet flushed,
     the note-off sends the note itself with its final duration. So durations
     reach the transformer separately from the note-on, possibly in a later
     iteration.
  e. Buffer input mode is different again (each note is sent at note-on, no quiet-gap
     batching). Not checked in detail.

How to make "one A per mass pull" reliable (not decided, for you to choose):
  - Option 1: make the producer push a whole flush as one unit (e.g. a batch push
    plus a "batch complete" marker/counter) and have the consumer only take
    complete batches.
  - Option 2: keep the FIFO as is and, in the new class, do a short "settle"
    drain: after the first token is seen, wait a few ms and drain again until the
    queue stays empty, then run A once.
  - Option 1 is exact but touches the shared input path (InputFilter /
    MidiInputProcess). Option 2 stays inside the new class but adds a small delay.

--- Batching: the options in more detail ---
Facts that matter (from the code):
  - inputTokenQueue is a CircularFifo<Token>, capacity 120. A push into a full
    queue drops the oldest token (it advances the read pointer from the producer
    thread). Pushes are one token at a time; there is no batch concept.
  - The producer: MidiInputProcess::timerCallback (message thread) builds one flush
    from notesOnToSend and calls sendTokensToMusicTransformer, which loops
    inputFilter->filter(token) -> PassthroughInputFilter -> InputFilter::pushToken ->
    inputTokenQueue.push(token) (and also pushes the same token to the OT queue).
    It prints two std::cout lines per token inside that loop.
  - The consumer drains with `while (pull)` once per run() iteration.
  - Why splitting is only a partial problem: A is deterministic over the window and
    replaces the window, so running it twice on a split burst ends in the same final
    R (the second run sees every note). What goes wrong is only the intermediate
    state: if run() generates a token right after the first part, the model is
    conditioned on a partial chord for that step, and A runs twice (extra CPU).

Option 0 - do nothing special.
  Drain, add to L/R, run A once per drain. A split burst gives two A runs and, at
  worst, one generation step conditioned on half a chord. Zero changes outside the
  new class. Simplest, but it does not meet "run A only once per burst" exactly.

Option 1 - producer batches (exact).
  Make one flush = one unit the consumer takes whole. Two ways:
    1a. Side channel: add a CircularFifo<int> of batch sizes. After the flush loop
        the producer pushes the number of tokens it just pushed. The consumer reads
        one size n, then pulls exactly n tokens (so it never takes half a batch).
        Existing reduction transformers ignore the size FIFO and keep draining token
        by token, so they are unaffected. Touch points: MidiInputProcess
        (sendTokensToMusicTransformer, and the note-off direct push in
        handleNoteOff), InputFilter (a filterBatch / batch-done call), and the new
        class. Risk: if a flush has more than 120 tokens, the oldest are dropped and
        sizes and tokens no longer line up, so the consumer needs a guard.
    1b. Change the queue element to a whole batch: CircularFifo<std::vector<Token>>.
        Naturally atomic, but it changes the type used by MusicTransformer,
        ReductionTransformerV1, V2, PianoReduction, InputFilter and AppSession.
  Note-offs still arrive separately (TokenUpdate via updatesFromFilter), so with
  either 1a or 1b the A re-run after a note-off (your answer above) is a second,
  separate trigger anyway.

Option 2 - settle drain inside the new class.
  After the first token of a pull is seen, wait a few ms and drain again; repeat
  until a drain returns nothing, then run A once. No change to the shared input
  path. Cost: a few ms of extra latency whenever input arrives. Not exact: a flush
  slowed by the std::cout lines or a busy message thread can still outlast the wait.
  The wait should be longer than one flush; removing the two cout prints per token
  would shrink the flush time a lot.

--- What happens when you play a 5 s fast passage (default settings) ---
(From reading MidiInputProcess.cpp; not run with live MIDI. Defaults: direct input,
directInputSendNoteOffs = true, directInputWindowLength = 10 = 0.1 s, start-on-input
off.)
  1. Each note-on is stored in notesOnToSend (keyed by pitch) with its real onset and
     a 10 ms timer is started. Every new note-on restarts the 0.1 s quiet-gap wait,
     so while you keep playing with gaps <= 0.1 s the timer flushes nothing.
  2. When you RELEASE a note, handleNoteOff sends it immediately (before any flush)
     as a normal token: real onset, final held duration. It is then erased from
     notesOnToSend. So in a fast passage notes stream into the reduction queue one
     at a time, at their note-off times, not in one flush after the passage.
  3. Consequences:
       - Notes arrive in order of RELEASE, not onset. With legato or overlapping
         notes (or a held bass), an earlier-onset note can arrive after later-onset
         notes.
       - There are few real "bursts". A pull usually holds the notes released since
         the last loop iteration (one iteration is about 25 ms of model time per
         token on the GPU, about 100 ms per generated 4-token note), so a pull can
         hold several notes at once, but only because they piled up, not because the
         producer grouped them.
       - Notes still held when the passage ends are flushed after the first quiet gap
         > 0.1 s since the last note-on, with the provisional 4 s duration; their
         note-off later arrives as a TokenUpdate. These are the only truly
         provisional notes.
       - In the existing transformers, the first token of each drain that has an onset
         EARLIER than entries already in inputData erases those entries and
         everything after them (applyQueuedInputToInputData, meant to rewind generated
         notes). With release-ordered arrival this can also drop earlier-received
         input notes that have later onsets. (From reading the code; not tested.) The
         new class must not copy that: L and R should insert notes by onset instead.
  4. Two caveats on my earlier summary:
       - "Pitch overwrite": notesOnToSend is keyed by pitch, so a second note-on of
         the same pitch overwrites the first only if there was no note-off between
         them. A keyboard sends a note-off on release, which sends and erases the
         entry first, so this basically cannot happen with default settings. I
         overstated it earlier.
       - If directInputSendNoteOffs were FALSE (not the default), a released unflushed
         note is just erased without being sent, so fast notes released before a
         pause would be lost.

--- KV cache for the mb model (ACTIVE again: mb, DA and T3 all use the committed + scratch paradigm) ---
STATUS: the earlier "remove the KV cache for now" is withdrawn. All three cached streams (mb /
T8, double anticipation / T7, and T3) use the committed + scratch cache described under 3.7.
The plan and measurements below are the mb-specific part (learned positions, reset at 256).
Policy: use a KV cache that grows as tokens are generated; when it reaches 256 tokens,
drop the oldest 128 and RESET the cache (rebuild it from the kept 128 tokens), then keep
growing to 256 again.
Why it must be a reset and not just slicing the cache: T8 uses learned position
embeddings (wpe), so each cached key/value carries the position it was computed at.
Slicing the cache leaves positions 128..255 in the cache and new tokens would collide
with them or go beyond 256 (never trained). Rebuilding at positions 0..127 keeps every
position consistent with training.
What I built (all in the scratchpad / on the remote host; nothing in virtual_orch):
  - A KV-cache ONNX of T8 exported on the remote host:
    ~/mb_t8_kv/mb_phase2_T8_best_step4000_kv.onnx (685 MB, on hai-res-mobile01, not
    downloaded). Inputs: input_ids, position_ids (explicit, because of wpe), past_key,
    past_value [12,B,12,P,64]. Outputs: logits, present_key, present_value. Verified
    against PyTorch: max |diff| 6.6e-4 (100-token prefill from an empty past) and
    1.7e-4 (40 single-token steps).
  - Results on the remote GPU (RTX 6000 Ada, GPU 1, shared with other jobs):
      * Extend 128 -> 256 tokens (128 single-token steps):
          - cache on the GPU between steps (IO binding): forward 14.1 ms/step, plus
            2.9 ms mask+sample = 2.18 s total = 58.7 tokens/s
          - cache copied CPU<->GPU every step (plain numpy): forward 20.1 ms/step,
            plus 2.8 ms = 2.93 s total = 43.7 tokens/s
          - no cache, full forward over a growing 129..256 window (forward only,
            no sampling): 2.45 s = 52.2 tokens/s
      * Cache reset (re-prefill 128 tokens at positions 0..127): 22 ms (IO binding)
        to 30 ms (numpy), once every 128 tokens.
      * Without IO binding the KV cache was NOT faster than recomputing the window.
        Most likely cause (not isolated): about 19 MB of cache is copied CPU<->GPU
        each way every step. With the cache kept on the GPU the forward pass alone is
        14.1 ms/step vs about 19.2 ms/step for the no-cache forward (2.45 s / 128),
        i.e. about 1.36x faster.
      * 128 tokens = 32 notes, so about 2.2 s per 32 notes of melody on the GPU.
      * Mac CPU with the KV model: not measured (the KV file is on the remote host).
  - Quality check on real data (4 concatenated phase-2 test lines = 1024 tokens, 723

      * B: just slice the cache, new positions = cache length: NLL 9.53, top-1 11%
      * C: just slice the cache, positions keep counting: NLL 10.46, top-1 17%
    A is the only KV variant that stays close to the current approach, which matches

--- What ~/orchestration does (read-only, src/orchestration/sampling/anticipation_sampler.py) ---
One shared sampler ("anticipation-style, AMT order") serves dense AMT, double
anticipation and phase 2. Loop:
  - Every control stream is a list of notes plus (instrument, delta_cs, priority). A
    control's ACTUAL time = onset - delta. All streams are merged in strict
    actual-time order; exact ties go to the lower priority number, then onset,
    pitch, velocity.
  - The event clock starts at 0. Before EACH event, every pending control with
    actual_time <= clock is inserted (tag CONTROL). Controls are never sampled:
    every control id is masked (-inf) at every event field, and the explicit control
    mask is applied again on top. No rejection sampling, ever. Controls whose actual
    time never comes up stay un-inserted (leftovers are not appended).
  - One event quad is then sampled field by field: onset in [min_onset, 9999],
    duration on the 5 cs grid (5..995), pitch only in the allowed event-instrument
    band(s), velocity on the 8-step grid (0..120). Per field: allow-list mask ->
    per-instrument logit adjustment on the PITCH field only (tau 0.5, tau' 0.5, 5 s
    window, each instrument's own notes; controls count as their own instrument) ->
    top-p 0.98 -> temperature 0.5 -> multinomial.
  - Stop when a sampled onset >= 15 s (offline only).
Double anticipation (da_spec): X = piano, instrument 0, delta 0, priority 1;
M = melody, instrument 2, delta 300 cs (3 s), priority 0 (M before X on exact ties);
events Y on instrument 1; clock = RestStepClock(100, visible=False), i.e. one clock
over the Y events plus HIDDEN 1 s rest steps: sample onset t; walk rest steps
r = prev + 100k with r < t; at the first r where a pending control becomes due,
discard t, move the clock to r, insert the due controls, resample with onset > r.
Rest steps where nothing becomes due change nothing (nothing is written). Optional
TD tokens (T7) go right after the first note quad whose actual time >= each 2 s
boundary. The code comment says DA models use the StreamingLLM cache (4 sink + 508).
Phase 2 / T8 (phase2_spec): prefix [ANTICIPATE], X'_mb as AMT control quads
(ATIME/ADUR/ANOTE/AVELOCITY ranges) with delta 0, events on instrument 1, VISIBLE
1 s rest quads. Same-onset controls are sorted like the training builder
(onset, raw duration, note).

--- CHANGE (from you): the 2 s window is time-based, with notes truncated to now ---
The window is now measured from the CURRENT time t (the app clock, right now) back to
t - 2 s, instead of from the newest onset. All notes are truncated to the current time
(a note's end is clipped to t). This replaces the earlier "2 s before the newest note's
onset" anchor (answer (i) to 2.3).
What follows from it (my reading, not tested):
  - Notes arrive at their note-off, so at arrival a note's end is about "now": a note is
    always inside the window when it arrives, even a long one that started earlier. The
    problem of a late note falling outside the window no longer exists.
  - Truncating at t only matters for notes whose recorded end is later than t. Those are
    the provisional (held) notes, which carry the 4 s placeholder duration. Clipping one
    to t gives its length so far. That conflicts with your earlier answer 2.1 (a),
    "held notes are excluded from A until note-off". See question 2.13.
  - R in the window = A(notes of L that sound inside [t - 2 s, t], each end clipped to t).
    When A re-runs at a later t, notes still held are longer, so their R entries change;
    entries older than the window are not recomputed and keep the version from the last
    run that covered them.
  - The mb "settled" idea (G-a below) becomes simple and time-based: a control is settled
    once it lies entirely before t - 2 s.

--- Requirement (from you): input to the mb model must be strictly monophonic ---
Any controls fed into the mb model (T8) must be strictly monophonic melody and strictly
monophonic bass: within the melody line no two notes overlap in time, and the same for the
bass line (melody and bass may overlap each other).
What algorithm A already guarantees (read from melody_bass.py): after the final
monophonic stage (_truncate_before_later_onsets then _monophonic_slices) exactly one note
owns each tick of each line, so each line has no overlaps. Melody notes are also removed
from the bass candidates.
Where this can break in the live version (my reading, not tested):
  1. The mb stream is append-only (and cached). Controls are inserted once past due and
     cannot be taken back. If R changes afterwards (a late note-off arrives, A re-runs,
     R's window is replaced), the controls already written into the mb context can
     disagree with R, and a late-arriving note whose onset is already behind the mb clock
     would be inserted out of onset order and could overlap a note already inserted.
  2. (No longer applies: held notes are now included in A, see 2.13. Originally:) Held
     notes were excluded from A until note-off (your answer 2.1). While a key is held
     the melody line has a gap, and a lower note may be picked as melody in that gap;
     when the held note finally arrives, A would drop that lower note, but it may already
     be in the mb context.
Proposed guards (for your approval):
  G-a. Insert a control into the mb stream only when it is settled: its onset is at least
       2 s before the newest onset in L (so A's window will never re-run over it), AND no
       held/provisional note has an onset at or before it (otherwise the melody clock
       waits for that note-off). Cost: about 2 s of lag, and melody generation pauses
       while a key is held.
  G-b. A final monophony check right before writing control quads: per line, a control
       must start at or after the previous control's end in the same line; otherwise it
       is shortened to fit or skipped. Cheap, and it protects against anything G-a misses.
Note: this concerns the controls (instrument 0) going into T8. T8's own generated melody
and bass (fed to the DA model as M) are not covered by this requirement.

--- What the two clock rules mean (worked example) ---
Setup: the model has generated reduction notes up to onset 1.0 s. You have played piano
notes at 1.5 s, 2.3 s and 4.0 s. The model now has to pick the next reduction note.
  LastEventClock (clock = onset of the last generated note, no rest markers):
    - The clock is 1.0 s. Only controls with onset <= 1.0 s are inserted. The model picks
      the next onset (say 5.0 s) WITHOUT having seen your notes at 1.5, 2.3 and 4.0.
    - Only after the note at 5.0 s is written does the clock become 5.0 s; then the
      controls at 1.5, 2.3 and 4.0 are inserted (past due), before the next note.
    - So controls may appear after a generated note that is later than them. That is
      exactly how the training data was built for this kind of model.
  Hidden 1 s rest steps (the double-anticipation rule):
    - The model proposes 5.0 s. The sampler walks 1 s steps after the last note: 2.0,
      3.0, 4.0. At the first step where a control has become due (your 1.5 s note is due
      at step 2.0), it throws the proposed onset away, moves the clock to 2.0 s, inserts
      the due controls, and asks the model for a new onset later than 2.0 s.
    - Nothing is written for the rest step itself ("hidden"), so the model sees the
      controls inside long gaps.
Which one is not a free choice: a model must be sampled with the clock it was trained
with. The README says T3 uses LastEventClock ("Event clock = onset of the last generated
event, starts at 0, no rests"), while the double-anticipation models (T6/T7) use hidden
1 s rests and the mb model (T8) uses visible rest quads. So for T3 the clock is
LastEventClock.

--- Consequence to confirm: T3 puts the piano controls on INSTRUMENT 3 ---
T3's final convention (README, "ctl3amt"): the user's piano controls are written as
instrument 3 (note band 11384..11511), the reduction events are instrument 1, and TD
tokens follow the anticipation rule. Your first description said "piano notes as

an "ant0" run) were trained with controls on instrument 0, so the instrument-3 band is
untrained in the dummy: the dummy can run and wire everything up but its output means

5. accompaniment mode = jam mode + max polyphony
=====================================================================
--- Description (from you) ---
  - Launchpad (7, 8) starts accompaniment mode.
  - Accompaniment mode is just jam mode, except that there is a MAX ALLOWED POLYPHONY
    when generating the instrument-1 tokens in the reduction transformer.
  - (7, 0) = max polyphony 1, (7, 1) = 2, (7, 2) = 3, (7, 3) = 4.
  - Meaning: at most that number of notes may be playing at once. If there are already
    >= max_polyphony notes sounding and the next note is to be generated, restrict its
    earliest possible onset to the next offset.

--- What exists (read from the code) ---
  - LaunchpadGrid (app/include/VirtualOrch/LaunchpadGrid.h): 8x8 grid, row 0 at the TOP.
    Row 0 = Edit (col 0) / Jam (col 1) mode pads; row 1 = TD level pads (cols 0..5) and
    the side pad = AUTO TD; rows 2-3 = user instruments (side pad of row 2 = flush); rows
    4-5 = model instruments; ROWS 6 AND 7 ARE UNUSED. The right-hand side column is
    index 9 in the code (kSideCol = 9, notes 19,29,...,89), and the top row CCs are
    104..111. Modes are the OrchestrationMode enum (Edit, Jam).
  - So (7, 0..3) are free pads. The code's side column is column 9, so "(7, 8)" is
    probably the side pad of the bottom row, but 8 is not a column index in the code.
  - Where the cap would apply: the reduction transformers sample the onset field with a
    mask that bans onsets before the current time (futureLogits). The cap would raise
    that lower bound when the number of sounding generated notes reaches the limit.

--- My reading of the rule (for your confirmation) ---
  Count the generated instrument-1 notes that are still sounding at the clock (onset <=
  clock < onset + duration). If count >= max_polyphony, the earliest allowed onset is the
  offset of the (count - max_polyphony + 1)-th earliest-ending of those notes. With
  count == max that is exactly "the next offset", as you said; with count > max (can
  happen if the cap is lowered while notes are sounding) the next offset alone would
  still leave too many notes.

--- Decisions (from you) ---
  - (7, 8) = the side pad of the bottom row (code: row 7 counting from 0 at the top, side
    column index 9). You count rows from 1, so you call the bottom row "row 8"; I take
    (7, 0..3) to be the bottom row's first four grid pads as well.
  - (7, 8) is a toggle that starts / stops accompaniment mode. It only applies while JAM
    mode is on. In EDIT mode it is not applicable, so it is not lit (and, as I read it,
    pressing it does nothing).
  - Max polyphony default on entering accompaniment mode: 1, i.e. pad (7, 0).
  - The cap applies to EVERY reduction transformer that generates instrument 1.
  - Only GENERATED notes count toward the polyphony (not the user's notes).
  - If more notes than the cap are sounding, the earliest allowed onset is the
    (count - cap + 1)-th earliest offset among the sounding generated notes (not just the
    next offset). Confirmed.

  - Also decided: the cap applies to BOTH generators in MelodyFirst (T8 melody and DA
    reduction); accompaniment mode and the polyphony choice are restored after Jam -> Edit ->
    Jam; pads (7, 0..3) do nothing while the mode is off; the selected polyphony pad is lit

  3.7 (answered by you, clarified: the model is NOT blind to a held note.) A provisional piano
      note IS used for inference, with the duration it has so far, but the cache is NOT
      advanced for it. My reading, as a two-layer cache:
        - COMMITTED cache: only confirmed tokens (everything before the first still-held
          control). It is the only thing that is stored and evicted.
        - SCRATCH tail: from the first provisional control onward, i.e. the provisional
          control(s) and every token generated after them. Each step the tail is fed on top
          of the committed cache to get the logits, and the resulting keys/values are NOT
          kept as committed. (The ONNX graph is a function: past in, present out, so using
          the committed tensors as the past and discarding the output is non-destructive.)
        - When the held note is CONFIRMED (note-off): replace its duration with the final
          one and advance the committed cache over the tail (re-feed from the committed
          prefix). There is nothing to rewind or slice, because the provisional tokens were
          never committed; the "rewind" is just re-feeding the tail.
      Why the generated tokens after the held control also stay in the scratch tail: their
      keys/values depend on that control being there, so they cannot be committed before it
      is confirmed.
      Costs (mb measurements, T3 not measured): re-feeding a tail of up to 128 tokens took
      about 22-30 ms on the GPU, about one forward pass; a tail grows by the tokens generated
      while a key is held, so a long hold makes each step longer, bounded by the window.
      Several held notes: the commit boundary is the EARLIEST still-held control; a later
      note confirmed first just gets its final duration inside the tail.
      (3.7b answered: (i) FROZEN: while a key is held, the duration of its control stays at
      the value it had when the control was written. (ii) a held note is COMMITTED as
      confirmed, with the duration so far, once it has been held for more than 10 seconds
      (a time limit, instead of my token-count idea of about 508 tokens).)
      Consequence of (ii): the commit boundary can never be older than 10 s; a note held
      longer is committed at 10 s with its duration at that moment and its later note-off
      changes nothing for the model. 10 s is also the longest duration token the
      vocabulary can hold (duration ids go to 9.95 s), so a longer duration could not be
      written anyway. The tail also has to fit the window: 10 s of generation is well
      inside 508 tokens only if the model writes fewer than about 50 notes in that time; if
      it would not fit, the earlier of the two limits applies (I assume, to confirm if it
      ever matters).
      Bookkeeping (how committed vs scratch is tracked; design only):
        - One logical token list for the stream. Each token carries: its id, the note it
          belongs to, and a provisional flag (set on the 4 tokens of a control whose key is
          still held, and on nothing else; tokens generated after a provisional control are
          scratch by position, not flagged).
        - committedLen = index of the FIRST token of the earliest still-provisional control
          (or the list length if none). Everything before it is final.
        - Two caches: C = keys/values for tokens[0:committedLen], only ever appended to or
          evicted (StreamingLLM: 4 sinks + recent rows); W = working cache = C plus the
          scratch rows (what was last computed on top of C). fedTokens = copy of the ids W
          was computed from.
        - Each step: compare fedTokens with the current token list; cut W back to the first
          difference (this only ever cuts scratch rows, never C), then feed the new/changed
          tokens on top and keep W. Sampling reads the logits of the last fed token.
        - Note-off: the duration token(s) of that control change, so W is cut back to that
          position and re-fed. If it was the earliest held note, committedLen moves to the
          next provisional control (or the end) and C becomes W up to that point.
        - With the duration frozen while held (3.7b i), the provisional tokens do not change
          between steps, so W is only appended to until the note-off.
        - Eviction: a counter of evicted rows maps token index to cache row; the 4 sink rows
          and the committed rows may be evicted from the front as usual; the scratch tail is
          never evicted from. If the tail grows past the window, 3.7b (ii) applies.
