## `offline-sim`: offline replay and operation logs (21 Nov)

- **`84b19cb` Offline log replay.** `LogReplay` runs a recorded session log through the app's real input,
  reduction (Hybrid), orchestration and playback code on simulated time. The models' random choices and external
  timing come from the log, and the output is compared with the recording tag by tag. To support this (no
  behaviour change when nothing is simulated):
  - `AppTime`: one simulated clock shared by everything that reads time (Clock, Launchpad repeat filter,
    pedal/activity times, hybrid rules, ahead throttle, OT balance, playback);
  - `SamplingRng`: an optional seeded generator for every sampler;
  - one-step loops: RT `beginLive`/`liveStep`, OT `beginSteps`/`stepOnce`.

  Also: `LogReplayTest`, plus two recorded sessions as test data.
- **`f73a483` Fix `modelsDir` shadowing.** In `createOrchestrationModel` a local `modelsDir` hid the
  `modelsDir()` function added in `6d90945`, so the file did not compile. The local is renamed to `projectDir`.
- **`56a4aaa` Operation logs.** The app writes `Documents/virtual-orch/Logs/oplogs/oplog_<start>.jsonl.gz`
  (`OpLog.h`), recording:
  - inputs, keys, pedal, and Launchpad presses with their effect, and the input window;
  - every change to the RT context (add / remove / rewrite / rebase, with reasons);
  - RT and OT draws with the chosen token's probability and the top-10 alternatives (`OpLogDraw.h`);
  - WAIT decisions, cuts, throttle and hybrid switches;
  - queue hand-offs, OT hold-back / calls / notes, and playback scheduling and drops;
  - every outgoing MIDI message.

  RT, OT and playback each checkpoint every 5 s, and a writer thread gzips the records every 100 ms.
  `tools/oplog_replay` backfills oplogs for old sessions by replaying them with every choice forced
  (resumable). Docs: `docs/LOG_REPLAY.md`.
- **`e50278c` `docs/OPLOGS.txt`.** Reference for every oplog record, its fields and ids, the checkpoints, how to
  split a launch into sessions, and what is not logged yet.
- **`9aef4cb` Oplogs match the docs.**
  - `MODE`, `OT_CALL` and the OT checkpoint name Edit "Step-in"; the RT checkpoint key is `step_in`.
  - `SESSION_END ops` is the true record count.
  - The session log keeps "Edit", so replays still compare with old recordings.

## `informative-wait`: the informative-WAIT model (overnight model 2) as a new reduction (22–23 Nov)

- **`1ef283f` The same `modelsDir` fix** as `f73a483` and `main`'s uncommitted change. `main` at `6d90945` does
  not build without it, and the identical diff merges cleanly.
- **`f423821` Informative WAIT: engine, reduction type 9, batched top-5 precompute.**
  - **`InformativeWaitEngine`** (no JUCE): the live port of the Python sampler
    (`orchestration/overnight/pkg/sample_overnight.py`).
    - Vocab 11879: `[WAIT d]` = 11768 + d/3 − 1 (3 cs grid, d ≤ 300); `[COUNT k]` = 11868 + k − 1;
      `[EXPIRED]` = 11878.
    - The fire window is [x−6, x+6]. A piano onset inside it plays exactly k stacked notes; an earlier one is
      ordinary input; no onset by x+6 writes EXPIRED.
    - Three modes: unconstrained; line A (legato, with a provisional `[WAIT x][COUNT 1]` after every note); line B
      (rests, plus its own WAIT with COUNT forced to 1).
    - Sampling: min-p 0.25 on duration, pitch and velocity; temperature 1.0 for onset, WAIT and COUNT and 0.5 for
      the rest; top-p 0.98.
    - Piano notes within 5 cs merge into one group. A piano onset cuts any not-yet-played generated note at or
      after onset − 5. The context is re-based to onset 0 past 500 tokens.
  - **Anticipation:**
    - While a WAIT is pending, the engine finds the top-5 first piano notes.
    - It tiles the KV state to 5 branches that decode the stacked notes, one call per engine step.
    - A fire on an anticipated note plays its branch at once.
  - **`StreamingKvCache`:** `BatchState`, `tileState`, `evictBatchForIncoming`, `OnnxBackend::runBatched` (host
    sessions), and `CommittedScratchCache::stateAfter`.
  - **App wiring:**
    - `InformativeWaitReductionTransformer` (inherits `ReductionTransformer`) and `MusicModelArch::DenseInformativeWait`;
    - AppSession wiring and the Reduction dropdown entry 9 "Informative WAIT";
    - checkpoint configs `w4_informative_wait{,_line_A,_line_B}.json`, which choose the mode.
  - **Tests (`InformativeWaitEngineTest`):**
    - the state machine on a scripted backend;
    - with the export present: batched == batch 1 (exact), and C++ == Python sampler probabilities (max 1.2e-5).
  - **`InformativeWaitOfflineSimTest`:** an offline simulation over the MAESTRO fixtures.
- **`8ade6ff` Live latency work; the configs load the p30_q03 model.** From the offline simulation on a 40 ms/call
  virtual clock:
  - **Commit fast path:** `CommittedScratchCache.reuseScratchOnCommit` (opt-in, set only by this engine) cuts newly
    committed rows out of the scratch state instead of re-feeding them: same logits within 4e-5, 4× fewer tokens
    fed. W3 and T3'' are unchanged.
  - **Held keys:** written with an estimated duration (median of the last 16 released notes) and not rewritten.
    `rewriteHeldDurations` restores W3's behaviour.
  - **Cheaper anticipation:** on its own KV copy, once per WAIT, 1 + 3k calls. `runBatched` takes n tokens per
    branch.
  - **Fires:** a branch's finished notes play at once and the rest decode one per step.
  - **Context cuts** wait until no WAIT is pending.
  - **Line A** skips legato fills that are already 10 cs in the past.
  - **Model:** the configs now load the p30_q03 model (the best p/q variant), now `simultaneous_model_v3.onnx`.

  Model file (renamed later to follow the folder's naming): `~/Documents/virtual_orch_models/simultaneous_model_v3.onnx`,
  KV + StreamingLLM with a dynamic batch axis, verified against PyTorch.

**Known limits of `informative-wait`:**
- Not opened by hand in the app with live MIDI.
- Accompaniment reordering of late input, Step-in's 2 s keep, and W3's logit biases are not ported. A mode cut
  restarts the stream.
- At about 40 ms per model call, dense passages leave too little time for the precompute (WAITs there are 6–27 cs).
  Fires are then decoded on the spot, about 20–25 cs to the first note.
- Line A cannot keep up with dense piano and drops fills.

**IodPretrainedExpressive's model** (`instrument_octave_predictions_v2.onnx`, 23 Nov evening) is in the app's own
format: 128-note windows and the compact combo layout, the same as v1. So no C++ change was needed. Today's training
code had switched to 64-note windows and a slot layout on 15 Oct; a first interim file made with it could not run in the
app and was replaced. On the robustness test it equals v1 on clean data and beats it everywhere else: up to 19% lower
loss on noisy, time-warped input. Details in that file's `.md`.
