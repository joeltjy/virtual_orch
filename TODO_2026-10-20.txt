1. BUG: in Edit mode note-offs are not applied; every note keeps the provisional length
=====================================================================
STATUS (20 Oct): DONE, not committed, not yet tried with a keyboard. Token::keyId
(MusicToken.h) is set per key press in MidiInputProcess, copied into orchestra notes by
InstrumentCombinations (by note index), IodPretrained and IodPretrainedTD (from the input
record; TestModel copies the token), and note-off updates match on it
(tokenMatchesUpdateSource) in OT applyTokenUpdates, OutputPlayback and the Playback
Output record. Duration only; the scaled velocity is kept (default 1.1). Tests:
test/source/KeyboardNoteOffTest.cpp (5, both test/ folders).
--- Description (from you) ---
  - In Edit mode the note-offs are not sent, and every note I play has the provisional
    note length.

--- What happens (read from the code; root cause found, not yet fixed) ---
  - A key that is still held when the 0.1 s direct-input window flushes is sent with the
    provisional duration (modelConfig.inputDuration, default 400 cs). On release,
    MidiInputProcess::handleNoteOff sends a TokenUpdate {oldNote, newNote} with the same
    onset / pitch / velocity and the real held duration.
  - The update reaches OrchestrationTransformer::applyTokenUpdates (every reduction class
    forwards it via orchestrationUpdatesIncoming), which pushes it to
    outputDurationUpdates. OutputPlayback::applyOneDurationUpdate then looks for the
    queued / sounding orchestra note with tokenEqualsByOnsetPitch, which requires the
    SAME onset, duration, velocity and pitch.
  - In Edit mode the user branch orchestrates the keyboard notes directly, and the
    orchestra note no longer equals the key that produced it:
      a. velocity: InstrumentCombinations and IodPretrained (decodeComboToNotes) write
         InstrumentConstants::scaleVelocityForInstrument(...) into token.velocity
         (brass scaled down, woodwinds up). Present since 6165586 (22 Sep).
      b. pitch: IodPretrained moves notes by an octave delta (basePitch + 12 * delta).
      c. onset: OrchestrationTransformer::snapNearbyOnsets averages the onsets of
         chord notes before getOutput.
    Any one of these makes the match fail, so the update is dropped and the note plays
    for the full 400 cs. Only strings with no octave shift and no chord can match.
  - Jam mode is not affected the same way: the reduction's generated notes are final
    when generated and get no note-off updates.

--- Plan ---
  1. Give every keyboard token a stable id when it is created (Token already has a
     noteId field, used today for reduction notes and vocsep restamps), and carry it in
     the TokenUpdate.
  2. Make each orchestration model copy the source token's noteId into every
     OrchestrationNote it produces from that token (IC, IodPretrained, IodPretrainedTD,
     TestModel), through snapNearbyOnsets as well.
  3. In OT applyTokenUpdates and OutputPlayback::applyOneDurationUpdate, match keyboard
     updates by noteId (fall back to today's field match when the id is -1), and only
     change the duration (keep the instrument's scaled velocity).
  4. Tests: Edit-mode chord, brass/woodwind instrument, and IodPretrained octave delta;
     each must get its note-off at the real release time.

--- Questions ---
  1.1 On a note-off update, should the orchestra note keep its scaled velocity (my
      plan) or take the key's velocity again? (Today the update would overwrite it.)

--- Description (from you) ---

--- Decisions (from you / agreed) ---
  - Draw it natively in JUCE, NOT VexFlow. VexFlow is JavaScript (would need a
    WebBrowserComponent + WebKitGTK and a JS bridge at ~100 Hz) and lays notes out by
    rhythmic value in measures (would need quantising durations and suppressing
    beams/rests/ties). A time-proportional rolling staff is a piano roll mapped onto a
    grand staff, in the style of PianoRollView / NoteIoWidget.
  - Chord names: use the vendored libs/chordnamer (CppChordNamer) after fixing it (you:
    "isn't too far off"). Not linked into the app yet. Causes found (tested on a copy in
    the scratchpad; libs/chordnamer itself is unchanged):
      a. "Dm/B" for B D F A: in the half-diminished branch "b5" is pushed to
         `additional`, so Bm7b5 gets ranking 1. Dm/B uses the rootless trick (the bass B
         is hidden, leaving a D minor triad, ranking 0) plus the slash penalty +1 = 1. On
         a tie the shorter name wins, so "Dm/B" (4 chars) beats "Bm7b5" (5). F6/B also
         ties and beats it. Fix: treat b5 as part of the m7b5 quality (append it after the
         extension, not in `additional`) -> Bm7b5 ranking 0.
      b. "C57" for C Eb G Bb: Note's parser takes the LAST character in a-g as the
         letter, so the flat sign of "Eb" is read as B -> Bb (also Ab, Db, Gb ... -> Bb;
         "Bb" is right by luck; sharps are fine). Fix: break on the first letter (and
         the upper-case range check `c <= 'g'` should be 'G'). -> Cm7.
      With a + b: B D F A -> Bm7b5, C Eb G Bb -> Cm7; C, C/E, G7, Cadd9, Adim7, Cdim,
      Db, Ebmaj7, Fmaj7, C6, Cm6, Dm7 unchanged.
      c. Not fixed: C D G -> "G5/C" (Csus2 second), same tie. Preferring root position
         on ties fixes it but breaks E G C (Em#5 instead of C/E), so it was dropped.
    Still to handle when integrating: it takes note-name strings (feed sharps, e.g.
    "D#", from MIDI pitch), throws std::length_error for fewer than 2 notes (skip those),
    and its CMake builds demo.cpp (with main()) into the static library (remove it from
    the library sources before linking).

--- Plan ---

  2. Layout: x = nowbarX + (onset - clock) * pxPerSecond; grand staff with middle C

  4. Chords (3.2): instrument-1 notes whose onsets are within 50 ms (5 cs) of each other

--- How it works now (read from the code, task 6 / 450bc43) ---
  - OutputPlayback::recordNoteOn (only for notes whose instrument has a MIDI channel)
    calls activityLog.noteOn(now, instrument, pitch, duration). ActivityLog maps the
    instrument to sectors (violin -> both violin sections; tremolo / pizzicato /

    sector on until the note ends + 2 s.

  - The widget polls activeSectors() at 20 Hz. SeatingPlanView::setActive rebuilds a
    full 1832 x 859 black overlay (65 % opaque over inactive sectors, from the pixel mask
    orch_seating_plan_sectors.png) pixel by pixel; paint resamples the full-size plan +
    overlay to the widget with high-quality filtering.

--- What was checked ---

  - Strings / woodwinds / brass all have a channel in the current map, so their notes

  - Cost in the Debug build: about 10 ms per overlay rebuild + 26 ms per paint at half
